# ТЗ — «Второй мозг»: дневник-консультант с многослойным анализом решений

> Технический слой к issue [#1](https://github.com/dansury/second_brain/issues/1).
> Пользовательский журнал (CJM) — см. приложение [`CJM.html`](./CJM.html).
> Промты по слоям анализа — папка [`Promts/`](./Promts).

**Статус:** черновик v1 (пишется в ветке `claude/festive-mendel-a71fza`).
**Стек, на котором строится реализация:** hermes-agent (Telegram-шлюз + LLM-агент)
+ gbrain (векторная память) + Grafify (граф кода, к продукту не относится) +
Yandex SpeechKit (STT/TTS) — см. `README.md`. Данное ТЗ описывает **надстройку**
над этим стеком, а не замену.

---

## 1. Цель и видение

Бот — персональный дневник и накопитель данных о пользователе, который со
временем превращается в консультанта: анализирует новые решения и сомнения
пользователя на основе накопленной истории (похожие ситуации, действующие
лица, исходы) и выдаёт **прогноз** — насколько решение похоже на удачное или
неудачное, и почему.

Ключевая идея: **вся информация проходит через многослойный анализ** прежде
чем осесть в базе — как для того, чтобы данные были структурированы (Obsidian,
`[[wiki-ссылки]]`, персоны), так и для того, чтобы сам анализ (риски, прецеденты,
прогноз) был воспроизводим, объясним и улучшаем по слоям независимо.

### 1.1 Не-цели (out of scope v1)

- Не заменяем hermes-agent/gbrain — используем их как ядро агента и память.
- Не строим собственный Telegram-клиент — используем существующий шлюз hermes.
- Не даём медицинских/юридических/финансовых гарантий — бот **не диагностирует**,
  а **сопоставляет с историей** и предлагает субъективную вероятностную оценку.
- Distinct “группы/каналы с несколькими людьми” не поддерживаются в v1 — только
  личный дневник-канал/чат пользователя (см. §4).

## 2. Термины

| Термин | Значение |
|---|---|
| **Vault** | Obsidian-база пользователя — папка markdown-файлов, синхронизируемая в персистентный том (`/opt/data/vault`) и опционально с git/Obsidian Sync. |
| **Персона** | Действующее лицо дневника. Файл `People/Имя_Фамилия_(роль).md`. |
| **Слой (layer)** | Один шаг многослойного LLM-конвейера обработки входящего сообщения. У каждого слоя — свой промт в `Promts/`. |
| **Решение / сомнение** | Запись, которую пользователь помечает (явно или по классификации слоя 3) как требующую консультации: «стоит ли…», «я сомневаюсь…», «принял решение…». |
| **Lint** | Проверка и нормализация markdown-заметки перед записью в vault: frontmatter, `[[связи]]`, дата, теги. |
| **Wiki (feedback-база)** | `Wiki/Feedback.md` (+ `Wiki/Feedback/<date>.md` при росте) — журнал причин 👎 и метаданных ответов. |

                     └────────────────────────┬───────────────---┘
                                              │
                                   ┌───────────┴──────────────┐

                                   │  Journal/ People/ Wiki/    │
                                   │  Handwriting/ Decisions/   │
                                   └───────────────────────────┘
```

Системный промт агента **склеивается из слоёв** в `Promts/` и пишется в
`${HERMES_HOME}/SOUL.md` — это нативный механизм hermes-agent для кастомной
идентичности агента (первый и самый приоритетный слой его system-prompt
assembly, см. [Prompt Assembly](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/prompt-assembly.md)
в документации hermes; произвольную папку с промтами напрямую hermes не
поддерживает — поддерживаются только `SOUL.md` + один project-context файл
(`AGENTS.md`/`HERMES.md`/…), поэтому сборка происходит на нашей стороне, в
`docker/entrypoint.sh`, см. §10.2). Агент сам «проигрывает» многослойный
конвейер в рамках одного диалогового хода, вызывая инструменты
`second-brain-mcp` на нужных шагах (в отличие от жёсткого pipeline-сервиса —
это даёт гибкость уточняющих вопросов, которых требует ТЗ на каждом шаге, и
не требует форка hermes).

**Почему не отдельный pipeline-сервис.** hermes-agent уже реализует
tool-calling ReAct-цикл с памятью диалога и STT/TTS command-провайдерами;
жёсткий детерминированный pipeline не даст боту задавать уточняющие вопросы
между слоями («кто на фото?», «чей это документ?»). Поэтому слои 2–9
реализованы как **промты + MCP-инструменты**, которые LLM оркестрирует сама,
а не как внешний оркестратор. Слой 0/1 (роутинг типа входа, транскрибация)
уже нативно делает hermes (Telegram message type + STT command-провайдер).

## 4. Источники входа

| Источник | Как подключается | Особенности обработки |
|---|---|---|
| **Канал-дневник** | Пользователь добавляет бота **администратором** канала. Бот читает новые посты через Telegram Bot API (`channel_post` update). | Публикатор = владелец аккаунта; персона по умолчанию — «я». |
| **Чат «Избранное» / чат с самим собой** | Пользователь добавляет бота в личный чат с собой (или пересылает сообщения из «Избранного» боту). | То же самое, но через `message`, не `channel_post`. |
| **Прямой диалог 1:1 с ботом** | Обычный чат. | Основной канал для вопросов-сомнений и уточняющих диалогов бота. |
| **Документы** | Пересылка/загрузка файла в любом из трёх источников выше. | Слой 5: бот уточняет, что за документ, прежде чем классифицировать и лить в vault. |
| **Фото** | Аналогично. | Слой 6/7 в зависимости от содержимого (люди vs рукописный текст vs документ-скан). |
| **Голос/видео/видео-кружок** | Аналогично. | STT (Yandex SpeechKit) → текст → далее как обычная дневниковая запись. |

Бот **мониторит** канал/чат-источник (polling новых сообщений через тот же
Telegram Update loop, которым hermes уже принимает личные сообщения — отдельного
демона не требуется, только право читать `channel_post`/групповые апдейты).

### 4.1 Импорт всей прошлой истории источника (слой 10)

Апдейты дают только то, что пришло **после** подключения бота: Telegram Bot API
историю чата не отдаёт. Поэтому при подключении источника (или по просьбе
владельца) отрабатывает слой 10 — тянет всю прошлую историю канала/группы в
vault, теми же датами, что у оригинальных сообщений.

| Путь | Когда | Инструмент |
|---|---|---|
| Публичное веб-превью `https://t.me/s/<username>` c пагинацией `?before=<id>` | публичный канал/группа с включённым превью | `import_chat_history` |
| JSON-экспорт Telegram Desktop (`result.json`) | приватный канал, группа, «Избранное» — превью нет | `import_chat_history_file` |

Тот же приём, что в GrowthProducer (`src/channels/history_import.py`): MTProto-клиент
не нужен, парсинг детерминированный, без LLM.

- **Идемпотентность двойная**: id импортированных сообщений лежат в
  `<vault>/.state/history-import.json`, плюс перед записью проверяется, нет ли
  постоянной ссылки на сообщение в файле дня — потеря состояния не даёт дублей.
- **Стоимость**: импорт сам по себе не вызывает модель. Через слои 2–4 агент
  прогоняет только свежий срез (`recent`, ≤20 записей), остальное осмысляется
  лениво — когда всплывёт в `search_vault`/gbrain как прецедент слоя 4c.
- **Догрузка**: `history_import_status` → `import_chat_history(since_id=max_msg_id)`.
- **Fail-soft**: сетевая ошибка или отсутствие превью не роняют импорт —
  возвращается собранное + `warnings`/`hint`, новые посты продолжают приходить
  апдейтами.

Записи истории попадают в `Journal/` с frontmatter `source: telegram-history`,
`via: tme-preview|tg-export`, `tg_chat: <username>`; в теле — текст сообщения,
автор (для групп) и постоянная ссылка на оригинал.

## 5. Многослойный конвейер анализа

Каждая входящая единица контента проходит по применимым слоям. Слои
**не все обязательны** — роутинг (слой 0) решает, какие слои задействовать.
Формат промта каждого слоя — см. `Promts/README.md`.

| # | Слой | Вход | Выход | Промт |
|---|---|---|---|---|
| 0 | Роутинг | Telegram-апдейт (тип, источник) | Тип контента + маршрут по слоям | `Promts/00_router.md` |
| 1 | Транскрибация | голос/видео/кружок | текст (STT Yandex, нативно hermes) + LLM-очистка | `Promts/01_transcription_cleanup.md` |
| 2 | Персоны | сырой текст записи | список упомянутых персон + результат сверки с базой (см. §6.2) | `Promts/02_entity_recognition.md` |
| 3 | Классификация | текст + персоны | тип записи: дневник / решение-сомнение / документ / фото-люди / рукопись / прочее | `Promts/03_classification.md` |
| 4 | Анализ решений (консультант) | текст помечен как «решение/сомнение» (или «исход» — 4f) | многослойный прогноз (см. §5.1); фиксация исхода прошлого решения (4f) | `Promts/04a…04f_*.md` |
| 5 | Документы | файл + подпись | уточняющие вопросы о типе документа → структурированная запись | `Promts/05_document_intake.md` |
| 6 | Фото с людьми | изображение | распознанные лица→уточнение «кто есть кто», позы, мизансцена, эмоции, анализ | `Promts/06_photo_people.md` |
| 7 | Рукописный текст | изображение | автор почерка (я/другой→кто), расшифровка, правки | `Promts/07_handwriting.md` |
| 8 | Obsidian lint | структурированный результат слоёв 2–7 | markdown-файл(ы) с frontmatter и `[[связями]]`, записанные в vault | `Promts/08_obsidian_lint.md` |
| 9 | Ответ + обратная связь | финальный ответ пользователю | сообщение + 👍👎; при 👎 — сбор причины, запись в wiki, предложение смены модели | `Promts/09_feedback_and_model_switch.md` |
| 10 | Импорт истории источника | подключение канала/группы или просьба «прочитай всё» | вся прошлая история в `Journal/` + срез свежих записей на осмысление (§4.1) | `Promts/10_history_import.md` |

### 5.1 Слой 4 в деталях — «многослойная структура анализа решений и сомнений»

Это ядро консультационной функции бота, явно запрошенное в issue как
**многослойное**. Раскладывается на 5 под-слоёв, каждый — отдельный проход
LLM (можно последовательно в одном тул-вызове агента, с явными
промежуточными результатами, чтобы каждый шаг был проверяем/логируем):

1. **4a — Экстракция решения.** Что именно решается, какие есть варианты,
   какой дедлайн/контекст, кто из персон вовлечён. `Promts/04a_extract_decision.md`
2. **4b — Факторы и риски.** Явные и скрытые факторы «за/против», риски,
   зависимости от вовлечённых персон (тянем связанные `People/*.md` и факты
   из gbrain). `Promts/04b_risk_factors.md`
3. **4c — Прецеденты.** Поиск похожих прошлых решений/записей в vault и
   gbrain (семантический поиск), их исходы (если помечены как решённые —
   см. `status: outcome-good|outcome-bad|open` во frontmatter решений).
   `Promts/04c_precedents.md`
4. **4d — Мультиперспективный прогноз.** Три независимых точки зрения —
   оптимистичная, пессимистичная, реалистичная — каждая аргументирует свой
   прогноз на основе 4b+4c. `Promts/04d_forecast_perspectives.md`
5. **4e — Синтез консультанта.** Финальная рекомендация: вероятностная оценка
   (не точное число, а качественная шкала: «скорее удачно» / «неоднозначно,
   зависит от X» / «есть значимый риск Y»), с явной ссылкой на прецеденты и
   факторы, которые на это повлияли. `Promts/04e_consultant_synthesis.md`
6. **4f — Фиксация исхода.** Когда пользователь сообщает, чем закончилось
   прошлое решение («в итоге…», «та затея провалилась»), слой находит запись
   через `search_vault` (`type: decision`, `status: open`), при неоднозначности
   уточняет у пользователя, какую именно, и проставляет исход инструментом
   `set_decision_outcome` (frontmatter `status: outcome-good|outcome-bad` +
   секция «Исход» со словами пользователя). Именно эти статусы питают
   прецеденты 4c — без 4f история не накапливает исходов и M2-консультант
   слепнет. `Promts/04f_decision_outcome.md`

Каждый под-слой обязан **процитировать**, на какие факты/прецеденты/персоны
опирался — это требование к промту, а не только к формату ответа: иначе
прогноз непроверяем и неотличим от галлюцинации.

## 6. Структура Obsidian-vault

```

├── Journal/                     # дневниковые записи, по датам
│   └── 2026/07/2026-07-13.md    # можно несколько записей в файл или per-entry — см. §6.1
├── Decisions/                   # записи-решения/сомнения (слой 4), со статусом
│   └── 2026-07-13-otpusk.md
├── People/                      # персоны, см. §6.2
│   └── Иван_Петров_(коллега).md
├── Documents/                   # присланные документы + резюме слоя 5
├── Photos/                      # копии + анализ слоя 6/7 рядом с фото
├── Handwriting/                 # профили почерков (слой 7)
│   └── Иван_Петров_почерк.md
├── Wiki/
│   └── Feedback.md               # журнал 👎 (слой 9)

### 6.1 Frontmatter журнальной записи

```yaml
---
type: journal              # journal | decision | document | photo-people | handwriting
date: 2026-07-13
source: channel            # channel | saved-chat | direct-dm | telegram-history
via: tme-preview           # только для source: telegram-history — tme-preview | tg-export
tg_chat: my_diary          # только для source: telegram-history — источник импорта
people: ["[[Иван_Петров_(коллега)]]"]
tags: [работа]
status: open                # только для type: decision — open|outcome-good|outcome-bad
---
```

### 6.2 Персоны и дизамбигуация

- Каждая упомянутая персона **обязательно** маркируется как `[[Имя_Фамилия_(роль)]]`
  в тексте заметки, и на неё существует отдельный файл `People/Имя_Фамилия_(роль).md`.
- Перед lint-ом слой 2 сверяет каждое упоминание с существующими файлами
  `People/*.md` (через `second-brain-mcp.lookup_character` — нечёткий поиск по
  имени/алиасам) и **если есть похожий, но не 100% совпадающий кандидат** —
  агент обязан спросить пользователя: «Это тот же Иван Петров (коллега), что
  уже есть в базе, или другой человек?» — прежде чем создавать новый файл или
  дописывать в существующий (реализуется промтом `02_entity_recognition.md` +
  инструментом `lookup_character`, который возвращает кандидатов с score).
- Файл персоны хранит роль, алиасы, дату первого упоминания, связанные записи
  (обратные ссылки Obsidian это даёт бесплатно через backlinks) и, если есть,
  ссылку на `Handwriting/*.md`.

## 7. Feedback (👍👎) и переключение модели

- Каждый ответ бота сопровождается запросом реакции 👍/👎 — по возможности
  Telegram inline-кнопками, если hermes-agent это поддерживает (см. открытый
  вопрос §13.5 — не подтверждено документацией на момент написания ТЗ); иначе
  fallback — текстовая реакция пользователя, которую слой 9 распознаёт так же.
- 👍 → тихо логируется (модель, слой, длина ответа) без вопросов пользователю.
- 👎 → бот спрашивает **что не так** (свободный текст), затем:
  1. пишет запись в `Wiki/Feedback.md`: дата, исходное сообщение/ответ,
     причина, **имя модели**, слой конвейера (если применимо);
  2. вызывает `list_models_by_price` (инструмент `second-brain-mcp`, тянет
     прайс из OpenRouter `/models` по текущему провайдеру) и предлагает
     список моделей **по возрастанию цены за токен**, с CTA `/model <id>`.

### 7.1 Три уровня выбора модели

Модель для слоя выбирается на трёх уровнях, приоритет **3 > 2 > 1**:

| Уровень | Что задаёт | Ключ в `model_prefs.json` |
|---|---|---|
| 3 — индивидуальный | модель конкретного слоя | `layers.<слой>` |
| 2 — по модальности | одна модель на все слои модальности | `modalities.<модальность>` |
| 1 — общий | запасной вариант для всего | `global` |
| — политика | `config/layer_policy.json` + каталог модальности | — |

Модальности: `text`, `ocr`, `vision`, `voice`, `video`. Слой относится к
модальности по `requires` из `layer_policy.json` (`file` → `ocr`, `image` →
`vision`, `audio` → `voice`, `video` → `video`), иначе `text`.

Уровни хранятся раздельно, поэтому выбор «одна модель на всё» **не сбрасывает**
слой, для которого модель выбрана вручную, — и наоборот. Если общая модель не
годится для модальности (текстовая модель не расшифрует `.ogg`), фолбэк берётся
не из неё, а из `default` каталога `config/modality_models.json`.

Каталог `config/modality_models.json` — что предлагать под каждую модальность
и по какой примерной цене за страницу / изображение / минуту / 1k токенов.
Он же питает кнопку «сменить нейросеть» в отчёте о нераспознанном.

Формат записи в `Wiki/Feedback.md`:

```markdown
## 2026-07-13 14:02 — 👎 (anthropic/claude-opus-4.6, слой: 04e)
**Причина:** прогноз не учёл, что коллега уже отказывался раньше
**Сообщение:** ...
**Ответ бота:** ...
```

## 8. Документы, фото-люди, рукописный текст

### 8.1 Документы (слой 5)
Бот **не** классифицирует документ молча — сначала задаёт уточняющие вопросы
(что за документ: договор/справка/скан/выписка/личное; кому/о чём). Только
после ответа — резюме в `Documents/` со ссылками на персон/решения, если
применимо.

### 8.2 Фото с людьми (слой 6)
Для каждого фото с людьми: (1) уточняющий вопрос «кто есть кто» по каждому
распознанному лицу, сверка с `People/*.md` как в §6.2; (2) анализ поз,
взаимного расположения, происходящего действия, выражений лиц; (3) финальный
анализ пользователю с 👍👎; (4) если 👎/правка — правка учитывается и **тоже**
пишется в `Wiki/Feedback.md`, а согласованный итог — в `Photos/`.

### 8.3 Рукописный текст (слой 7)
Если на фото есть рукописный текст: (1) вопрос «чей это почерк» — варианты
«мой» / «другого человека → чей именно» (сверка с `People/*.md`); (2)
распознавание + предложенная расшифровка; (3) 👍👎 + правка пользователя;
(4) **запоминание начертания букв** для конкретной персоны в
`Handwriting/<Персона>_почерк.md` (описательно — характерные особенности
начертания, а не биометрический шаблон) для будущих расшифровок этого же автора.

> Замечание к реализации v1: точное распознавание почерка и лиц по фото
> требует vision-модели с OCR/face-анализом (мультимодальный LLM через
> OpenRouter, напр. `anthropic/claude-*` или `google/gemini-*` с image input —
> уже доступны через существующий `/model`). MCP-инструменты `analyze_photo_people`
> и `handwriting_lookup/-remember` в этой итерации — это **память и
   дизамбигуация** (см. §10.1), сам визуальный анализ делает LLM-слой агента
> нативно (image input в hermes), промт направляет его выводы в нужный формат.

## 8.4 Архивы (слой 11)

Владелец присылает **один zip**: экспорт группы, канала, переписки с человеком
или с нейросетью — вместе с документами, фотографиями и голосовыми; либо архив
Obsidian-базы по Karpathy. Разбор идёт этапами и с предварительной сметой,
потому что контейнер на amvera маленький, а архив может быть на гигабайты.

Порядок:

1. **Инспекция без распаковки** — `inspect_archive`. Оглавление zip читается по
   central directory: имена, размеры, вид файла, «вкус» архива. Архив целиком в
   память не поднимается никогда.
2. **Вкус** решает маршрут:
   - `obsidian_vault` (доля `.md` ≥ 0.6 **и** есть `[[вики-ссылки]]`) —
     распознавать нечего, заметки пишутся как есть, сразу слой 8 (lint);
   - `telegram_export` (`result.json`, `messages*.html`, каталоги `photos/`,
     `voice_messages/`) — переиспользует §4.1;
   - `chat_export` (`conversations.json`, `*_chat.txt`) — экспорт нейросети
     или мессенджера;
   - `generic` — произвольный архив.
3. **Смета до запуска** — этапы, объём в единицах биллинга, токены, время,
   примерная цена по каждому этапу и итог. Владелец соглашается или нет.
4. **Этапы в порядке возрастания стоимости и неопределённости**: текст →
   документы (OCR) → изображения (vision) → голос (STT) → видео. Внутри этапа —
   батчи; между батчами контейнер отдыхает; на файл — таймаут.
5. **Прогресс** — одно самообновляющееся сообщение с прогресс-баром;
   `archive_report` отдаёт готовую строку бара и разбивку по этапам.
6. **Нераспознанное** — файл в vault **не пишется** и попадает в отчёт с тремя
   выходами: сменить нейросеть (со списком подходящих под эту модальность и
   ценой под объём именно этого файла), описать своими словами, выбросить.
   «Выбросить» поэтому и означает «этого файла в базе нет».
7. **Ошибки** видит только владелец бота, не тот, кто грузил архив.

Состояние разбора (что обработано, что провалилось, что выброшено) лежит
в `$DATA_DIR/archive_state.json` — рестарт контейнера не теряет очередь.

## 9. Промты

Все промты слоёв — в `Promts/*.md`, один файл = один слой/под-слой, с
одинаковой структурой (роль, вход, обязанности, формат вывода, запреты).
Конвенция именования: `NN[letter]_имя_слоя.md`, где `NN` — номер из таблицы
§5. `Promts/README.md` — оглавление и правила добавления нового слоя.

`Promts/*.md` — источник истины, редактируется отдельно от инфраструктурного
кода и проходит git-review независимо. **hermes-agent не читает произвольную
папку с промтами напрямую** — единственные поддерживаемые точки инъекции
кастомного system-prompt-контента: `${HERMES_HOME}/SOUL.md` (идентичность
агента, первый и самый приоритетный слой) и один project-context файл
(`AGENTS.md`/`HERMES.md`/…, первый найденный). Поэтому `docker/entrypoint.sh`
конкатенирует `Promts/*.md` в заданном `Promts/README.md` порядке и пишет
результат в `${HERMES_HOME}/SOUL.md` при каждом старте контейнера (§10.2) —
файл в персистентном томе перезаписывается, редактировать нужно `Promts/*.md`
в репозитории, а не `SOUL.md` в томе напрямую.

## 10. Технические компоненты

### 10.1 Новый MCP-сервер `second-brain-mcp`

Отдельный процесс (Node.js/Bun, по аналогии с gbrain — тот же рантайм уже
в образе), поднимается как ещё один `mcp_servers.*` в `config.yaml`,
как `gbrain`/`grafify`. Владеет vault-ом на файловой системе.

Инструменты (MCP tools) — первая итерация:

| Tool | Назначение | Слой |
|---|---|---|
| `lookup_character(name, role?)` | нечёткий поиск персоны в `People/`, возвращает кандидатов + score | 2 |
| `upsert_character(name, role, aliases?)` | создать/обновить `People/Имя_Фамилия_(роль).md` | 2, 8 |
| `obsidian_write_entry(type, frontmatter, body, links[])` | lint + запись markdown-файла в нужную папку vault-а | 8 |
| `search_vault(query, type?, status?)` | текстовый/метаданный поиск по vault (доп. к семантическому gbrain); фильтр `status` — решённые прецеденты для 4c / открытые решения для 4f | 4c, 4f |
| `set_decision_outcome(ref, status, note?)` | проставить исход решения: frontmatter `status` + секция «Исход» | 4f |
| `record_feedback(rating, reason?, model, layer?, context)` | запись в `Wiki/Feedback.md` | 9 |
| `list_models_by_price(provider?)` | список моделей провайдера, отсортированный по цене промпт-токена (дергает `/models` OpenRouter) | 9 |
| `remember_handwriting(person, notes)` | добавить/обновить заметки о почерке персоны | 7 |
| `get_handwriting_profile(person)` | получить накопленные заметки о почерке для подсказки при расшифровке | 7 |
| `import_chat_history(chat, limit?, since_id?, dry_run?)` | вся история публичного канала/группы через `t.me/s` с пагинацией → `Journal/` (§4.1) | 10 |
| `import_chat_history_file(file, chat?, limit?, since_id?, dry_run?)` | то же из JSON-экспорта Telegram Desktop — приватные каналы/группы/«Избранное» | 10 |
| `history_import_status(chat?)` | что уже импортировано: количество, диапазон id, время прогона — для догрузки и защиты от повторов | 10 |
| `inspect_archive(file, dry_run?)` | оглавление zip без распаковки: виды файлов, вкус архива, смета по этапам (токены, время, ≈цена) | 11 |
| `archive_stage_files(file, stage, offset?, limit?)` | очередной батч файлов этапа — по нему конвейер и идёт | 11 |
| `archive_read_file(file, entry, as?)` | содержимое одного файла архива: текст или base64 для картинки/аудио | 11 |
| `archive_mark(file, entry, status, note?)` | отметить файл обработанным / провалившимся / выброшенным; состояние переживает рестарт | 11 |
| `archive_report(file)` | прогресс-бар, разбивка по этапам, список нераспознанного с вариантами моделей и ценой под объём | 11 |
| `set_model_preference(level, value, model)` | записать выбор модели на одном из трёх уровней (§7.1); уровни друг друга не затирают | 9 |
| `get_model_preferences(layer?)` | что сейчас выбрано и какой уровень решил конкретный слой | 9 |

v1 (M1) реализует персоны, vault, feedback и модели — то, что даёт
статически-проверяемую пользу без vision-моделей; два handwriting-инструмента —
заготовка API, наполняется по мере вывода в прод слоя 7. M2 добавляет
`set_decision_outcome` и фильтр `status` в `search_vault` (слои 4c/4f).

### 10.2 Изменения в существующей инфраструктуре

- `docker/entrypoint.sh`: новый блок `second_brain_mcp_block()` — регистрирует
  MCP-сервер `second-brain` (аналогично `gbrain_block`/`grafify_block`); и
  функция `write_soul()` — конкатенирует `Promts/*.md` в порядке из
  `Promts/README.md` и перезаписывает `${HERMES_HOME}/SOUL.md` при каждом
  старте (единственный поддерживаемый hermes способ задать кастомную
  идентичность агента, см. §9).
- `config.yaml` (пример в `config/hermes/config.example.yaml`): добавляется
  `mcp_servers.second-brain`.
- `Dockerfile`: `COPY Promts/ /opt/second_brain/Promts/`,
  `COPY tools/second-brain-mcp/ /opt/second_brain/tools/second-brain-mcp/` +
  установка зависимостей (bun install, тот же рантайм что и gbrain).
- `env.example`: новые переменные — `VAULT_PATH` (по умолчанию
  `/opt/data/vault`), `SECOND_BRAIN_MCP_ENABLED`.
- Приём `channel_post`-апдейтов из канала-дневника (§4): требует, чтобы
  hermes-agent обрабатывал такие апдейты нативно, когда бот — админ канала
  (типично для Telegram Bot API ботов); отдельного poller-а в этой итерации
  не пишем. **Не подтверждено документацией hermes** — см. открытый вопрос
  §13.7: если нужна явная белый-список настройка источников, добавится
  `INGEST_CHANNEL_ID`/`INGEST_SAVED_CHAT_ID` в `TELEGRAM_ALLOWED_USERS`-стиле.
  Прошлая история от этого не зависит: её тянет слой 10 (§4.1) через веб-превью
  или экспорт, а не через апдейты.
- `scripts/`: `scripts/vault.sh` — статус/бэкап/сброс vault-а (по аналогии с
  `scripts/memory.sh` для gbrain).

## 11. Нефункциональные требования

- **Приватность.** Vault и wiki-feedback — персональные данные пользователя;
  хранятся только в персистентном томе (`/opt/data`), не логируются во внешние
  системы кроме выбранного LLM-провайдера (OpenRouter/Yandex) для самого
  анализа. `TELEGRAM_ALLOWED_USERS` обязателен в проде (см. `env.example`).
- **Идемпотентность lint-а.** Повторная обработка одного и того же сообщения
  не должна плодить дубликаты персон/файлов — `lookup_character` и
  `obsidian_write_entry` детерминированы по нормализованному ключу
  (slug имени+роли, дата+источник для журнала).
- **Отказоустойчивость распознавания.** Если STT/vision-слой не уверен —
  промт обязан переспросить пользователя, а не молча писать в базу
  низкокачественный результат (общее правило для слоёв 1, 6, 7).
- **Язык.** Все промты и пользовательские сообщения — русский (ru-RU),
  согласовано с уже настроенным `YANDEX_STT_LANG=ru-RU`.
- **Наблюдаемость.** Каждая запись в `Wiki/Feedback.md` — единственный
  обязательный минимум телеметрии по качеству ответов в v1 (без внешней
  аналитики).

## 13. Открытые вопросы

1. Нужен ли отдельный git-репозиторий/Obsidian Sync для vault-а, или
   достаточно персистентного тома amvera (бэкапится ли том сейчас)?
2. Порог нечёткого совпадения персон (score) для авто-слияния vs обязательного
   уточняющего вопроса — предлагается: >0.92 — тихо считаем той же персоной
   для существующих алиасов, 0.6–0.92 — переспрашиваем, <0.6 — новая персона
   без вопроса. Нужно подтверждение продукт-владельца.
3. Хранить ли оригиналы фото/голоса в vault (`Photos/`, `Journal/media/`) или
   только текстовые résumé — влияет на объём персистентного тома.
4. Формат вероятностной оценки в слое 4e (шкала слов vs число) — см. §5.1,
   предварительно выбрана качественная шкала во избежание ложной точности.
5. **Inline-кнопки 👍👎 в hermes-agent не подтверждены документацией** —
   публичная документация hermes описывает Telegram как один из
   поддерживаемых мессенджеров шлюза, но не описывает API для inline
   keyboard в ответах агента. Требуется проверить фактическую поддержку
   (возможно, через MCP tool-response с разметкой, либо это ограничение,
   требующее текстового fallback: реакции пользователя эмодзи-реакцией на
   сообщение вместо inline-кнопки, или текстовые команды `+`/`-`). До
   подтверждения — слой 9 (`Promts/09_feedback_and_model_switch.md`)
   реализован в тексте-независимой форме (просит текстовую реакцию), чтобы
   не блокироваться на неподтверждённом UI-примитиве.
6. `agent.personalities` (именованные персоны hermes, session-level overlay
   через `/personality`) в v1 не используется — весь конвейер задаётся через
   `SOUL.md`. Возможное расширение: вынести слои 4d (три перспективы) в
   отдельные `personalities`, если понадобится ручное переключение точки
   зрения консультанта пользователем.
7. Обрабатывает ли hermes-agent `channel_post`-апдейты (посты в канале, где
   бот — админ) так же нативно, как личные сообщения, или нужна отдельная
   настройка/whitelist источника? Не подтверждено публичной документацией —
   уточнить до реализации M1-приёмника канала-дневника (§4, §10.2).

**Закрыто.** «Нужен ли MTProto-клиент, чтобы прочитать историю канала до
подключения бота?» — нет. Публичные каналы/группы читаются с веб-превью
`t.me/s`, приватные — из JSON-экспорта Telegram Desktop; оба пути реализованы
в слое 10 (§4.1) без второго Telegram-клиента и без хранения телефонной сессии.
